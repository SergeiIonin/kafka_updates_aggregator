# Критический анализ проекта Kafka Updates Aggregator

Дата анализа: 2026-07-13. Версия: v0.1.0 (README).

## TL;DR

Идея здравая и решает реальную проблему (денормализация/join событий из нескольких Kafka-топиков
в один по ключу, с самообслуживанием схем через REST). Но **в текущем виде сервис не работает
end-to-end** — есть баг, который блокирует единственный механизм, которым Schema Registry
доносит схемы до Redis-индекса, используемого агрегатором. Плюс есть busy-loop, сжигающий
ядро CPU впустую, отсутствие консьюмер-групп (нет горизонтального масштабирования), полностью
открытый REST API без аутентификации, обработка ошибок через `panic`/`log.Fatal` на пользовательских
данных (self-inflicted DoS), и полное отсутствие CI/Docker/health-checks/метрик.

Как учебный/pet-проект — нормально, показывает понимание Kafka, консьюмер-групп, паттерна
merge-by-timestamp, Schema Registry. Как что-то, что можно катить в прод — нет, нужен раунд
исправлений критических багов и решение о зрелости инфраструктуры (CI, наблюдаемость, graceful
shutdown) прежде чем говорить про какой-либо SLA.

## 1. Критический баг: пайплайн синхронизации схем не работает

`kafka_schemas_handler/keytypes/KeyTypes.go:29-32`:

```go
if isValidKeytype(keytype) {
    return "", fmt.Errorf("keytype %s is not supported", keytype)
}
return keytype, nil
```

Условие перевёрнуто: если keytype **валиден** (`SCHEMA` или `DELETE_SUBJECT`) — функция возвращает
ошибку "not supported" и **не пропускает сообщение** в `KafkaSchemasHandler.Run`, где по ошибке идёт
`continue` (`kafka_schemas_handler/KafkaSchemasHandler.go:42-46`). Если keytype **невалиден** —
функция считает его валидным и возвращает как есть, но он не попадает ни в один `case` в `switch`
(там нет `default`), то есть тоже тихо игнорируется.

Итог: **ни одно** сообщение из топика `_schemas` не обрабатывается. Это разорванное звено всей
цепочки:

```
REST API → Schema Registry → топик _schemas → KafkaSchemasHandler → Redis (field → schema index)
                                                                          ↑
                                                          KafkaAggregator читает отсюда
```

Без записей в Redis `KafkaAggregator.WriteAggregate` (`kafka_aggregator/KafkaAggregator.go:191`)
всегда получает пустой список схем для любого ключа — агрегированные топики никогда не создаются.
Это ядро продукта, и оно не работает.

Проверил эмпирически юнит-тестом (без Docker/Kafka, только сама функция):

```
keytype="" err=keytype SCHEMA is not supported
```

Интересно, что `kafka_schemas_handler/TestKafkaSchemasHandler_test.go` — интеграционный тест
через testcontainers — по идее должен был поймать эту регрессию (пишет валидное `SCHEMA`-сообщение
и ждёт появления схемы в Redis, с таймаутом 25с). Скорее всего он либо не гонялся (в репозитории
нет `.github/workflows` — CI отсутствует вовсе), либо падал и на это не смотрели. Отсутствие CI —
отдельная системная проблема (см. раздел 6).

**Это нужно чинить в первую очередь**, до любого обсуждения производительности или security.

## 2. Другие корректностные баги

- **`kafka_aggregator/KafkaAggregator.go:220`** — `errors.Is(err, fmt.Errorf("no value"))` никогда
  не сработает: `fmt.Errorf` каждый раз создаёт новый объект ошибки без `Is`/`Unwrap`, сравнение
  идёт по указателю. Задуманный "пропускаем схему без значений" пропуск не работает — вместо этого
  код пытается писать `kafka.Message{}` (пустое сообщение с пустым `Topic`) в Kafka, что просто
  тихо логается как ошибка записи на каждый неполный набор полей. Нужно завести sentinel-ошибку
  (`var ErrNoValue = errors.New("no value")`) и сравнивать с ней.

- **`kafka_merger/ChannelsMerger.go:49-52`** — busy-wait без сна:
  ```go
  for {
      if len(pq) == 0 {
          continue
      }
      ...
  }
  ```
  Это спин-лок, который сжигает 100% одного ядра CPU постоянно, независимо от нагрузки (даже когда
  очередь пуста бóльшую часть времени). На проде это прямые расходы на CPU и шум в CPU-based
  автоскейлинге/алертинге. Плюс `len(pq)` читается **без** `mutex.Lock()`, тогда как запись в `pq`
  идёт под мьютексом в горутинах-читателях выше (строка 31-33) — это гонка данных, которую поймает
  `go test -race`. Нужно селектить по каналам/таймеру вместо активного опроса.

- **`kafka_aggregator/KafkaAggregator.go`** — почти вся обработка ошибок on the hot path — это
  `panic(...)`: неправильный JSON в ключе сообщения (строка 86, 91, 95), ошибка похода в Redis
  (строка 150), ошибка парсинга типа поля (строка 157). Любое "грязное" сообщение в топике
  (не по вине сервиса — прислал сторонний producer) кладёт весь процесс. Поскольку офсет в
  kafka-go коммитится в момент `ReadMessage` (а `GroupID` тут вообще не задан — см. ниже),
  краш-цикл на poison message не гарантированно самовосстановится сам, а если и восстановится
  за счёт пропуска — это неявная потеря данных.

- **`kafka_aggregator/KafkaAggregator.go:25-30`** — у `kafka.Reader` не задан `GroupID`. Это значит:
  сервис нельзя горизонтально масштабировать (несколько инстансов не смогут поделить партиции
  через consumer group — они либо будут дублировать чтение, либо конфликтовать), и нет
  персистентного оффсета между рестартами через штатный механизм Kafka consumer groups.
  Для сервиса, который называется "aggregator" и потенциально в проде должен переживать рестарты
  и скейлиться — это существенный архитектурный пробел.

## 3. Производительность — где упрёмся в потолок

- **Отсутствие батчинга.** `kafka_merger/KafkaMerger.go:104-108` — `BatchTimeout: 1 * time.Millisecond`
  на Writer практически отключает батчинг kafka-go (по одному сообщению за раунд-трип). Это резко
  увеличивает нагрузку на брокер (гораздо больше produce-запросов на то же количество данных) и
  сажает throughput. Обычно для этого паттерна нужен батчинг в десятки миллисекунд.

- **Синхронная запись без пайплайнинга.** И в `KafkaAggregator`, и в `KafkaMerger` запись в Kafka —
  это `writer.WriteMessages(ctx, msg)` по одному сообщению за раз, блокирующе, в одном потоке
  обработки. Пропускная способность одного процесса ограничена RTT до Kafka + RTT до Redis (N
  запросов Redis на сообщение — `Get`/`Upsert` на каждое поле, `kafka_aggregator/KafkaAggregator.go:146,198`)
  + запись во столько топиков, сколько схем совпало. Никакого пайплайнинга/конвейеризации нет.

- **Write amplification.** Одно входящее событие с K полями, где каждое поле участвует в N схемах,
  триггерит до N синхронных записей в Kafka на **каждое** входящее сообщение, даже если реально
  изменилось только одно поле из схемы (`WriteAggregate` не проверяет, что именно изменилось —
  комментарий `// todo it's better to ensure that we write only in case there's un update...`,
  `kafka_aggregator/KafkaAggregator.go:216`, признаёт это сам автор). При росте количества схем на
  поле стоимость одного события растёт линейно.

- **CPU spin-loop** (раздел 2) — постоянная фоновая нагрузка независимо от трафика, чистые накладные
  расходы на инфраструктуру.

- **Логирование на хот-пути.** Практически каждая строчка обработки сообщения логается через
  `log.Printf`, включая полные payload'ы (`log.Printf("payload %s", string(payload))`,
  `kafka_aggregator/KafkaAggregator.go:166`, и похожее в мерджере/хендлере). Синхронный вывод в
  stdout на каждое сообщение — это ощутимые накладные расходы под нагрузкой и рост объёма логов
  пропорционально трафику, без какого-либо уровня логирования (нет debug/info/error разделения,
  всё зашито как `// fixme rm` — то есть сам автор понимает, что это временный мусор).

- **Redis без TTL.** `FieldsRedisCache.Upsert` (`kafka_aggregator/fieldscache/FieldsRedisCache.go:29-31`)
  пишет hash по ключу `id` без какого-либо `EXPIRE`. Каждый уникальный `id` (например, user_id)
  создаёт постоянно растущий hash в Redis, который никогда не чистится. Это неограниченный рост
  памяти Redis пропорционально количеству уникальных пользователей за всё время жизни системы —
  жёсткий потолок по памяти, который наступит тем раньше, чем успешнее продукт.

**Практический потолок:** при таком дизайне (один читающий поток на сервис, без consumer group,
без батчинга, с синхронными Redis round-trip'ами на каждое поле и spin-loop'ом в мерджере) реалистичная
пропускная способность — низкие сотни сообщений в секунду на инстанс, и масштабировать это
горизонтально сейчас нельзя (см. `GroupID` выше), только вертикально — то есть потолок довольно низкий
для системы, которая позиционируется как агрегатор Kafka-топиков.

## 4. Security

- **REST API полностью открыт.** `cmd/restapi/main.go:71-72` — `POST /create` и `GET /schemas` без
  единой проверки авторизации, аутентификации, CORS-политики или rate limiting. Любой, у кого есть
  сетевой доступ к сервису, может:
  - зарегистрировать произвольную схему (а значит, заставить `KafkaAggregator` начать писать в
    произвольный топик, имя которого приходит от него же — `subject` не валидируется, кроме как
    JSON-биндингом, `restapi/infra/SchemaDTO.go`);
  - прочитать список всех существующих схем-подписантов (потенциальная утечка структуры данных
    платформы — какие поля/сущности вообще трекаются).
  Если это internal-only сервис за отдельным периметром — приемлемо, но это нигде не
  задокументировано и не enforced на уровне кода (ни middleware, ни sidecar-assumption в конфиге).

- **Отказ в обслуживании через "грязные" сообщения.** Как отмечено в разделе 2, `panic` на
  невалидном JSON в ключе Kafka-сообщения — это буквально DoS "one bad message crashes the
  consumer", инициируемый кем угодно, кто может писать в исходные топики.

- **Отсутствие транспортной защиты.** Нигде в клиентах Redis (`redis.NewClient(&redis.Options{Addr: ...})`,
  без `TLSConfig`), Kafka (`kafka.TCP(...)`, без SASL/TLS) или похода к Schema Registry
  (`srclient.CreateSchemaRegistryClient(schemaRegistryUrl)`, без basic auth/TLS-опций) нет даже
  поддержки шифрования/аутентификации на уровне кода — то есть даже если захотеть включить TLS
  к брокеру в проде, для этого сейчас нет конфигурационных полей.

- **Отсутствие валидации входных данных.** `SchemaDTO`/`FieldDTO` принимают произвольные строки
  `Type`/`Name`/`Subject` без ограничения длины, допустимых значений типа (сравнение идёт со свитчем
  строк в `getFieldTypedValue`, `kafka_aggregator/KafkaAggregator.go:118-138`, неизвестный тип просто
  тихо ловится как ошибка на каждое сообщение) или количества полей — нет защиты от чрезмерно
  большого/глубоко вложенного JSON.

## 5. Архитектурная оценка идеи

Идея — держать "производные" топики, агрегирующие поля из нескольких исходных топиков по общему
ключу, с self-service регистрацией схем через REST — вполне рабочий паттерн, его закрывают Kafka
Streams (KTable joins), ksqlDB, Flink, Materialize, или что попроще — Benthos/Redpanda Connect.
Причина, по которой эти инструменты существуют и почему их обычно предпочитают самописному решению:
корректный инкрементальный join/агрегация под сбоями (exactly-once, water marking, backpressure,
переприсваивание партиций) — сложная и хорошо изученная задача, и в этом проекте она решена
частично и с багами (heap-merge по времени в `ChannelsMerger`, без сохранения состояния между
рестартами, без dедупликации, без консьюмер-групп).

Как pet/learning-проект — здоровая инициатива: видно, что автор осознанно взял на себя Kafka
consumer groups, backoff-тюнинг, testcontainers e2e-тесты, Schema Registry интеграцию — это
неплохой охват для демонстрации навыков. Но "взлетит" в смысле продакшен-системы — сейчас нет,
пока:
1. не починен keytype-баг (без него функция вообще не работает);
2. не появится решение — либо доводить hand-rolled merge/aggregation до продакшен-качества
   (батчинг, consumer groups, TTL, graceful shutdown, метрики), либо честно признать, что это
   тонкий слой поверх Kafka Streams/Flink и не изобретать join заново.

## 6. Эксплуатационная зрелость

- **Нет CI** — ни `.github/workflows`, ни любого другого пайплайна. Тесты (включая e2e через
  testcontainers) не гоняются автоматически, что напрямую объясняет, почему критический баг
  из раздела 1 не был пойман.
- **Нет Dockerfile/docker-compose**, хотя сервис по своей природе — набор из 4 демонов + зависимости
  (Kafka, Redis, Schema Registry) — сейчас непонятно, как это вообще поднять одной командой для
  разработки или демонстрации README-примера.
- **Нет graceful shutdown.** Все `cmd/*/main.go` стартуют с `context.Background()` без обработки
  `SIGTERM`/`SIGINT` — под k8s это будет hard kill каждый раз при деплое/скейлинге, плюс `log.Fatalf`
  и `panic` в рантайме обходят любую очистку ресурсов (закрытие Kafka-коннектов, Redis-клиентов).
- **Нет health/readiness эндпоинтов**, метрик (Prometheus и т.п.) или трейсинга ни в одном из 4
  сервисов — эксплуатировать это в оркестраторе (k8s liveness/readiness, HPA) нечем.
- Разбросанные по коду `// fixme`, `// todo` в горячих путях (`KafkaAggregator.go:65,73,77,166,184,206,214`
  и др.) указывают, что сам автор считает текущее состояние debug/WIP, а не финальным.

## 7. Итоговые приоритеты (если продолжать проект)

1. Починить `keytypes.GetKeytype` (1 строка, но без неё продукт не функционирует).
2. Убрать `panic`/`log.Fatal` из обработки данных, пришедших по сети — заменить на логирование
   + метрику + либо retry, либо dead-letter, но не падение процесса.
3. Убрать spin-loop в `ChannelsMerger`, поправить гонку по `pq`.
4. Добавить `GroupID` в `KafkaAggregator`, продумать партиционирование/масштабирование.
5. Добавить TTL/эвикцию для Redis-хэшей в `FieldsRedisCache`.
6. Настроить батчинг Kafka-writer'ов под реальную нагрузку вместо `BatchTimeout: 1ms`.
7. Добавить CI (хотя бы `go vet`, `go test -short`, а лучше и e2e с testcontainers в GitHub Actions),
   Dockerfile/compose для локального запуска.
8. Решить вопрос с аутентификацией REST API, если сервис не строго internal-only.
9. Добавить graceful shutdown, health-checks, базовые метрики перед тем, как рассматривать прод.
